# 技术架构

> 状态：D1–D13 已确认调整已按授权落实代码、示例与用户说明；实际验证及未完成外部验收见 [实施计划](ImplementationPlan.md)。 终端展示方案已实施，见第 2.4 节及实施计划。

本文落实 [产品需求](PRD.md)，不继承旧方案的技术设计。功能行为以 PRD 为权威，本文件定义实现组织与技术约束。

## 1. 总体组织与目录

项目名为 **Research**，是可直接修改的本地研究模板，不采用 `src/` layout，不建立多层领域包。公共 Python 包及目录为 `core` / `core/`，CLI 名称为 `research`；工具名与公共包名独立，不再使用 `deepbench`。

```text
项目根/
├─ core/               # 实验管理、默认训练、CLI 等公共能力
├─ methods/            # 模型与方法代码
├─ dataio/             # 研究数据准备、读取与划分代码
├─ configs/            # TOML 实验配置
├─ notebooks/          # 探索与使用示例
├─ scripts/            # Bash / Slurm 薄封装
├─ data/               # 数据及准备产物
├─ experiments/        # 实验与分析产物
├─ tests/              # 模板自身的精简验证
└─ docs/
```

- `dataio/` 承担研究侧数据准备与读写，避免顶层 `datasets/` 遮蔽 Hugging Face 同名包。
- 小方法可用一个文件，实际变大后再拆小目录；不预建深层结构。
- `core/` 先按职责组织模块，只有实际需要才增加子目录，不预先规定大量服务层或接口类。
- CLI 和 Notebook 复用普通 Python 功能。CLI 不承载研究逻辑；Notebook 不另建执行系统。

## 2. 配置、CLI 与路径

### 2.1 配置读写与校验

- 配置统一使用 TOML，由 `tomlkit` 读写，只使用需要的能力；生效配置快照和调参导出也使用 TOML。
- 支持少量点路径参数覆盖，不建立配置继承或组合语言。
- Pydantic 仅覆盖模板拥有的公共配置：检查必要类型、默认值和未知字段，避免静默类型转换。
- 研究专属参数作为普通字典交给方法，不强迫每个组件定义 schema。方法按需检查跨参数约束，其余尽量保留构造函数或依赖库原生报错，不静默丢弃参数。
- 校验集中在入口与关键正确性条件，不在调用链各层重复防御；不吞异常，不在失败后自动切换参数、平台或加载方式。

公共默认值边界（已落实）：取消 seed、数据名/路径、主指标、方向和 epoch 上限的隐含值，按 PRD 第 5.2 节在实际用到时校验；示例显式填入所用值。保留 device=cpu、output=experiments、空名称/标签/备注、keep_top_k=1、早停关闭及剪枝 none。不批量取消库内部或示例方法自己的默认参数。

### 2.2 命令入口

采用 Typer，根据命令参数调用共享 Python 函数，不建设通用命令注册框架。配置读取、运行、查询、比较等能力可以由 Notebook 直接调用。

实验组采用 `research group create/run/test` 子命令组，替代 `group-create/group-run/group-test`，不保留重复旧入口。其他单词命令不强制分层，`--clear-tags` 等选项仍用连字符。相关 Notebook、README 和测试已同步；现有训练启动脚本无这些旧命令，无需修改。

### 2.3 路径语义

配置中的相对数据、模型和输出路径统一相对项目根目录解释，也支持绝对路径。CLI 与 Notebook 使用同一规则。根目录默认从模板项目位置确定，必要时显式指定；不通过 `chdir()` 改变整个进程工作目录。具体根目录定位实现保持简单。

### 2.4 终端展示与显式 JSON 导出

本节落实 PRD 第 5.10 节，仅改变展示和用户主动导出，不改研究计算或实验记录。讨论 Q137–Q151 已收敛，以下布局已实施，使用后可再微调。

#### 展示与数据分离

- Typer 继续负责命令解析，表格和进度使用 Rich 原生组件，不手工拼边框。将 `rich>=15.0.0` 列为直接依赖（以确认时 uv.lock 的 15.0.0 为下限），依赖列表保持字母排序，不借此升级其他依赖。
- 展示读取既有完整结果，不修改返回对象、不将格式化字符串写回 JSON/JSONL/CSV，也不从终端输出反向生成实验记录。查询派生信息不等于 record.json 原文；JSON 导出保存该命令的完整返回结果。
- 终端浮点数统一 `.6g`（6 位有效数字），小量自动科学计数显示；seed、计数保持整数。不存在的值显示 `—`，不能与零混淆。持久化保留原数值，不按终端精度舍入。
- 标题和标签采用英文；颜色只作辅助，状态和警告均有文字。ID、错误、备注等长文本允许换行，不主动截断；空列表显示 `No matching records.`。不添加交互选择、分页、列配置或主题系统。

#### 查询和分析布局

| 命令 | 默认终端内容 |
|---|---|
| `list` | ID、类型、方法、数据集、seed、状态、名称；不适用字段为 `—`，不展开嵌套历史 |
| `show` 普通实验 | 基本信息、标签/备注；最终指标表及结果来源；来源关联；启动编号、状态、起止时间、恢复来源组成的历史表；当前及历史错误按所属启动展示 |
| `show --folder studies` | 基本信息、完成/失败/剪枝数量、未结束说明；trial 编号、状态、目标值、参数、运行 ID、重试来源表；长错误在表下按 trial 编号展示，不省略 trials |
| `show --folder groups` | 基本信息、名称/标签/备注、已有错误；成员 ID 与状态表 |
| `compare` | 指标标题及 ID、方法、数据集、seed、数值表；已有训练设置和协议差异另列，不引入新的可比性判定 |
| `summarize` | 指标标题及样本数、均值、样本标准差表 |
| `paired` | 指标、检验名称、双侧约定、配对数；左右两侧均值/样本标准差表；left − right 平均差值、p 值、计算状态及未计算原因 |

详情不默认展开完整环境信息和启动命令等底层字段，但导出保留。未填写来源或备注时不显示整块空区域。比较的既有不兼容警告必须醒目保留，整表不可混合汇总的语义不变；不自动分组、打优胜标记、加显著性星号或推导研究结论。

#### 显式保存

- `list`、`show`、`compare`、`summarize`、`paired` 提供 `--save PATH.json`，不提供 `--json`。默认仍显示可读表格；指定保存时额外写出完整机器可读 JSON，不套入屏幕布局或另建分析记录。
- 相对路径沿用项目根语义；不自动命名文件或管理报告目录。已存在目标需 `--overwrite`，仅替换指定输出文件，沿用第 6.3 节覆盖边界。
- `compare --csv`、图片及 TOML 导出保留，不用 JSON 替代。保存成功显示完整目标路径，例如 `Saved JSON: /path/to/report.json`；失败直接报错，不显示成功、不自动改名或覆盖。
- Python 查询/计算返回结构不变。CLI `--save` 使用返回结果直接序列化，不能为导出再次运行实验或重复计算统计。

#### 训练和测试的运行展示

| 流程 | 开始摘要 | 执行期间 | 结束摘要 |
|---|---|---|---|
| 默认监督训练 | 实验 ID、方法、设备、保存位置 | 一个 epoch 级 Rich 进度条，显示当前/总 epoch、已用时间、最近完整轮次的训练 loss 和验证主指标 | 状态、已有验证选优指标、保存位置 |
| 自定义训练 | 同上 | 研究方法自行决定；不根据 run.log 次数猜进度 | 状态、方法返回的最终指标、保存位置 |
| 独立测试 | 同上，增加来源 checkpoint | 无进度条，不额外遍历数据 | 状态、本次测试指标、保存位置 |

非交互终端（包括 Slurm 输出、重定向）使用每个完整 epoch 一行的普通文本，不写动态刷新控制字符。失败结束显示错误原因并保持原异常传播；不能展示旧结果为本次成功结果。不增加 batch 级进度或额外计算指标，不改变按完整 epoch 恢复、早停及无操作恢复的既有行为。Optuna 调参保留原生输出，不接管其日志，也不为 trial 自动开启上述训练展示。

实现位于 `core/display.py`：普通函数显示查询表格，`RunDisplay` 仅负责运行摘要和 Rich 进度。CLI 向共享 runner/group 入口显式传入展示对象，Python 默认不启用；默认监督循环通过可选 `on_epoch` 反馈已保存轮次，自定义方法无新增接口。JSON 导出由 `analysis.save_json` 直接序列化既有返回值。`core/records.py`、平台适配、方法代码和 checkpoint 格式未改。

开始/结束和进度均为终端反馈，不另建落盘副本；自定义方法的现有日志、checkpoint 和运行历史照常保存，不要求它实现新生命周期或进度接口。实现采用最小的共享展示代码，不建设事件总线或通用回调框架。

## 3. 研究方法与数据接入

### 3.1 显式方法映射

- 使用一处普通 Python 名称映射，将配置的方法名映射到实现，仅加载实际选中的方法，避免未使用方向的依赖阻塞运行。
- 不扫描文件、不做装饰器注册、插件发现或类型化 Catalog；不分别注册每个模型层、loss、优化器和数据加载器。
- 新方法增加研究代码、配置和必要的映射项，不改 CLI 分支或实验管理核心。

### 3.2 默认构建与自定义入口

常规方法提供构建函数，直接通过 Python 创建模型、数据加载器、优化器、可选 scheduler、batch 计算函数和指标函数，交给默认监督流程。独立测试仅构建模型、测试数据和评估所需对象，不强迫创建训练集或优化器。

特殊方法使用普通 Python 函数拥有自己的完整循环，并按需调用轻量实验对象提供的记录和 checkpoint 等服务。不要求继承 Trainer、实现空接口或模拟一组生命周期钩子；不预先抽象强化学习流程。

常规入口为 `build(config, root) -> core.training.Training`、`build_test(config, root) -> Evaluation`、`load_checkpoint(model, file, state=None)`。自定义入口为 `run(config, run, root, trial=None)`，自定义测试为 `test(config, run, root, file, state=None)`。数据准备可选 `prepare(config, root)`；反序列化可选 `load_state(file)`，职责见第 6.2 节。不增加基类或注册框架。

### 3.3 数据复用

数据准备、读取和划分使用普通研究函数，由方法调用；不另建数据组件注册框架。配置可以选择数据集与路径，CLI 只传递配置，不为每个数据集添加分支。

同一任务的多个数据集可共享规范化读取逻辑，不同原始格式在准备阶段转换；模型专属处理由方法实现。数据集和划分标识进入记录，供筛选与可比性检查，不以通用格式或缓存系统替代研究者选择。

### 3.4 数据目录推荐约定

```text
data/
├─ raw/
│  ├─ dataset_a/       # 原始数据
│  └─ dataset_b/
├─ dataset_a/          # 处理后的数据
└─ dataset_b/
```

- `raw/` 集中存放本地原始数据，预处理不得覆盖原文件。
- 处理产物直接按数据集放在 `data/` 下，不额外增加 `processed/` 层。
- `dataio/` 只放数据准备、读取、划分代码，不放实际数据。
- Hugging Face 下载的数据继续使用其默认缓存，无需复制进项目；自行加工的产物可放入上述数据目录。
- 这是推荐约定，不是强制结构；允许通过配置指定其他位置。不新增缓存或目录管理机制，也不预建空目录。

## 4. 默认监督流程的最小契约

### 4.1 循环职责

- 默认支持一个模型、一个优化器和一个可选 scheduler，均由方法构建；复杂更新顺序交给自定义循环。
- 默认循环负责模型设备放置、训练/评估模式、梯度开关、反向传播、优化器更新、验证、早停和 checkpoint 调用。
- batch 函数接收指定设备，由方法按自己的数据结构搬运 batch，不实现通用递归搬运器。
- scheduler 每轮验证后更新：`ReduceLROnPlateau` 使用配置的验证主指标，其他 scheduler 调用 `step()`；按 batch 更新的策略由自定义循环处理。
- 默认不接入 AMP 控制，不为未来精度或分布式功能预建钩子。

### 4.2 batch 计算结果

batch 函数负责读取 batch、前向计算及可选 loss 计算，不负责反向传播或更新优化器。返回普通字典，字段如下：

| 字段 | 训练 | 验证/测试 |
|---|---|---|
| `loss` | 必需，保留梯度的标量均值 | 可选 |
| `weight` | 必需，为 loss 平均所用分母 | 提供 loss 时必须同时提供 |
| `predictions` | 可省略，默认不收集 | 必需，指标所需 Tensor |
| `targets` | 可省略，默认不收集 | 必需，目标 Tensor |

- epoch loss 按 `sum(batch_loss * weight) / sum(weight)` 汇总；按样本平均时权重为样本数，按有效 token 平均时为有效 token 数，不由模板猜测。
- 默认训练只汇总 loss，不额外收集整套训练预测或增加对应开关。
- 验证/测试的预测和目标脱离梯度、转到 CPU，沿第 0 维拼接后传给指标函数。默认只支持可如此拼接的 Tensor，不建立嵌套结构或变长输出合并系统。
- 指标函数返回名称到数值的映射，由方法解释 logits、概率等输入，不预先统一转成类别。不将 batch F1/AUC 简单平均。
- 内存无法容纳或输出不适合上述契约时，使用自定义评估，不预建流式指标框架。

### 4.3 训练与评估差异

默认复用同一个 batch 计算函数；仅前向或 loss 不同时可分别提供训练、验证/测试函数。存在测试时更新、多优化器交替等流程差异时，使用自定义循环，而非持续增加阶段钩子。

独立测试从管理 JSON 定位 checkpoint 和所属启动，读取该启动的 `config-N.toml`。测试配置选择数据、协议、设备与平台等评估设置，模型参数仍须与来源匹配；训练设置自动取该 checkpoint 所属启动的配置（包括恢复时调整的 epoch 上限），不要求用户手工复制。合成后的实际配置保存在测试自己的启动快照，来源记录保存实验 ID、checkpoint 路径与启动号；后续比较不再依赖来源目录仍然存在。外部 checkpoint 无来源实验时只使用用户明确提供的完整配置，来源实验与启动号为空，不猜测训练设置。

## 5. 记录、恢复与 checkpoint

### 5.1 产物目录

```text
experiments/
├─ runs/          # 训练、自定义运行及独立测试，以类型区分
├─ studies/       # Optuna 搜索
├─ groups/        # 轻量多 seed / 多配置实验组
└─ reports/       # 比较表格及图表
```

记录使用标准库 UUID 生成唯一 ID，不增加严格递增 UUID 依赖；名称、方法、数据集、标签等存在元数据中，不再按这些维度套多层目录。测试关联来源训练与 checkpoint，study/group 引用成员 ID，不复制成员目录。没有 persistent Handle、封存、派生修订或资源管理平台。

### 5.2 文件格式

| 内容 | 格式 |
|---|---|
| 生效配置、启动配置快照、调参导出 | TOML：`config.toml`、`config-N.toml` |
| 运行信息、状态、最终指标、标签、备注 | JSON：`record.json` |
| 逐条追加的指标历史 | JSONL：`metrics-N.jsonl` |
| 日志 | 文本：`log.txt` |
| checkpoint 管理信息 | 小型 JSON：`checkpoint.json` |
| checkpoint 研究状态 | PyTorch：`checkpoint-启动号-epoch-唯一后缀.pt` |
| 预测和特殊产物 | 方法按需决定 |

直接读取目录元数据完成查询，不建立数据库索引、事件回放或完整审计系统。`record.json` 的 `result` 保存供比较的指标，`result_source` 显式保存来源类型及有效完成启动号：

- `validation_best`：默认监督流程结束时，从有效验证历史按主指标选择结果；另记 `metric_launch` 与 `epoch`，允许最佳指标来自更早启动。
- `custom_final`：自定义方法返回的最终数值指标字典，不要求过程日志或 checkpoint，即使有验证日志也不改用它选结果。
- `test`：该次独立测试的结果。

比较直接读取 `result`，使用 `result_source.launch` 对应的启动配置。训练恢复从 4 epoch 延长至 10 epoch 后，按完成启动的 10 epoch 配置比较，即使最佳指标出现在早期。测试的实际配置已自动包含来源 checkpoint 启动的训练设置。`data.name` 与协议共同参与可比性校验；表格展示数据集及训练设置，数据集/协议不一致时整表每行均显示不可混合汇总的警告，并保留数据集与协议字段，汇总和检验拒绝。不将单行判为错误，也不自动分组或修正。路径不充当数据身份。

### 5.3 启动记录与恢复路径

每次实际初始运行或恢复在同一实验下记录轻量启动编号、当次生效配置、起止状态，以及恢复来源。默认监督指标带启动编号与 epoch，不要求累计 batch step；自定义流程可使用自己的尺度。日志和指标追加保留，不为恢复删除历史。已达到 epoch 上限的无操作恢复在新启动记录与平台初始化前正常返回，遵循 PRD 第 5.3 节。

JSONL 读取仅跳过“最后一行解析失败且没有结尾换行”的残行，原文件保留；其他解析错误直接暴露，不猜测或修复内容。这不替代下面的有效历史筛选；无 checkpoint 的自定义流程沿用完成状态与最终结果规则。

中断前可能已产生尚未进入 checkpoint 的指标。恢复后重跑时，绘图和比较按照恢复边界使用实际续训路径上的有效完整结果，不把旧的中断片段或重复 epoch 当成新样本；原始记录保留供排错。无需任务管理或通用事务机制，但实现必须验证此边界。

恢复时允许的配置变更及覆盖语义见 PRD 第 5.3 节与第 3.3 节。

### 5.4 研究状态与管理信息分离

`checkpoint.json` 保存最近续训状态的 `file/epoch/launch` 及 `top` 列表；Top-K 条目另含 `score`。研究状态单独写入 `.pt`，不嵌入管理 JSON。`checkpoint_info(directory, selection)` 仅读 JSON 定位 `last`、`best` 或保留的 Top-K 文件，`checkpoint(...)` 返回路径。`last` 与 Top-K 独立保留引用，必要时可指向同一状态文件。

`Run` 初始化与 `history` 只读管理信息，按启动的恢复来源追溯有效记录。完整入口在真正恢复时调用方法加载函数，将返回对象放入内存中的 `run.last["state"]`；磁盘管理 JSON 不包含它。默认循环收集普通模型、优化器、scheduler、RNG、早停及显式 `stateful` 组件状态，自定义方法提供自己的状态。公共接口为 `Run.log(values, epoch=None, split="validation", *, step=None)` 与 `Run.save_checkpoint(state, epoch=None, score=None, *, step=None)`；必须选择 epoch 或自定义 step 之一，不同时维护两套计数。默认流程仅写 epoch；自定义 step 进入日志、管理信息及恢复边界，不猜测其含义。有排名 score 时必须配置方向。不建立 StateProvider 注册或自动状态发现体系。

写入严格按以下顺序：
1. 每次保存使用全新文件名（同一启动/epoch 重复保存也不复用名字），写好研究状态；
2. 原子替换 `checkpoint.json`，发布新状态及 Top-K 引用；
3. 清理原管理信息中不再被 `last` 或 Top-K 引用的旧文件。

发布前中断保留旧引用及原内容；发布后中断可留下旧文件，但新引用已指向写好的状态。允许未引用文件残留，不引入清理服务或通用事务。不提供旧 `last.pt` 布局或缺少显式结果来源记录的自动迁移；旧产物原样保留，需要时由研究者显式处理或新建实验。

### 5.5 状态展示与实验组元数据

- 普通运行文件保存最后写入状态；查询发现 running 且目录锁空闲时派生 interrupted，不写回磁盘。Ctrl+C 的既有失败分类不另改。
- study 可有并行启动，未闭合启动展示“有未结束记录，当前是否仍在运行未确认”，同时显示 complete/fail/pruned 数量与未结束 trial；保留原始记录，不加心跳或自动判死。
- 实验组成功后移除组级旧 error，失败时更新当前 error；成员历史不因此清除。
- 创建成员时合并已有 study/trial 来源与 group ID，成员配置及运行来源均保留；手动配置仅增加 group，不加 manual 标记或来源图。组名称/标签/备注默认空，使用 `annotate --name/--tag/--note`（Python 同名参数）填写，不建立组配置系统。

## 6. 文件写入与可信加载

### 6.1 写入保护

- 重要状态文件先写临时文件，写完后替换目标文件，减少半成品风险，不保证断电持久性或磁盘故障恢复。
- 每个实验输出目录同一时间只允许一个模板写入者；写入或覆盖前获取轻量目录级锁并在运行期间持有，显式覆盖不绕过锁。
- 采用退出或崩溃后由操作系统释放锁的机制，不要求用户清理残留锁标记。
- 使用 `filelock.FileLock` 的操作系统文件锁；锁位于输出类别下的 `.locks/ID.lock`，不随目标覆盖而删除。不自行实现 PID、心跳、失联进程检测或陈旧锁清理。
- 保护只约束遵守锁规则的模板进程，不防外部手工修改，也不承诺所有网络文件系统具有相同锁语义。

测试覆盖复用上述保护，覆盖范围见 PRD 第 5.4 节。

### 6.2 制品加载

在 [可信输入边界](PRD.md#34-信任边界) 内，优先采用依赖库已有安全加载能力，不建设安全序列化框架：

- 常规模型、Tokenizer 和 `safetensors` 使用标准加载流程。
- `trust_remote_code=True` 由研究者明确启用，模板不自动开启。
- 受支持的 Tensor 和普通状态字典优先使用 `torch.load(..., weights_only=True)`。
- 方法可提供普通可选函数 `load_state(file)`，返回研究状态，自行明确决定反序列化方式；可信特殊 Python 对象可在该函数内显式使用 `weights_only=False`。恢复、来源 checkpoint 测试及外部 checkpoint 测试均使用该入口，核心不会预先强制安全反序列化。无该函数时使用 `core.records.load_state` 的 `weights_only=True`，失败直接暴露，不自动降级、识别格式或建立加载器注册。`load_checkpoint` 负责将已加载状态应用于模型，自定义 `test` 直接接收状态。embedding 本身不必然需要关闭限制。
- 安全权重格式不代表模型、依赖或执行行为得到全面安全保证。

### 6.3 导出覆盖

CSV、图片与调参配置导出统一默认拒绝已有目标文件。CLI 提供 `--overwrite`，Python 提供 `overwrite=False`；显式启用只替换指定输出，不影响来源实验，不清理目录或自动备份。

## 7. Optuna 与批量执行

### 7.1 搜索范围与方法扩展

- 配置中的 `search.space` 支持 Optuna 原生 `float`、`int`、`categorical` 分布参数，搜索路径限定 `params.*`。已确认保持此范围，不扩大到数据集、`data.params.*` 或其他公共字段，不增加数据重建或缓存能力。
- 条件和派生参数可由方法的 `suggest(trial, config_dict)` 实现，返回完整配置字典，但只允许改变 `params`；公共配置仍经过校验。
- 默认目标是有效验证历史中主指标的最优值，不使用测试结果。研究者也可通过指标函数提供综合标量，或用 `objective(config, run_directory, trial)` 明确计算单一目标。
- `supports_pruning = True` 只声明实际支持；自定义循环仍需调用 Optuna 原生报告与剪枝接口，不因声明而自动具备剪枝能力。

### 7.2 剪枝策略

已实现：`search.pruning` 使用策略配置表，不再接受旧布尔写法，不自动迁移旧配置。

```toml
[search.pruning]
strategy = "median"  # 省略时为 "none"

[search.pruning.params]
n_startup_trials = 5
n_warmup_steps = 0
interval_steps = 1
n_min_trials = 1
```

上例为当前 Optuna 原生默认值，可省略参数表或只指定部分参数。配置入口读取 MedianPruner 构造签名补全默认值，校验整数类型、未知字段及 Optuna 原生取值约束；`none` 不接受参数。解析后的策略与完整参数进入 study/启动/trial 配置和导出配置。继续同一 study 不允许改变该配置。

- 仅支持 `none` 与 `median`，默认 `none`；分别使用 Optuna 的 NopPruner 和 MedianPruner。
- `median` 允许设置其原生参数，并将实际使用的策略与参数保存到生效配置。未显式设置的原生默认值应在解析时明确并记录，不把示例数值宣称为普遍适用的研究设置。
- 默认监督流程以 epoch 为 Optuna 中间报告接口的 step（不是累计 batch step）；自定义方法负责明确自己的报告尺度。MedianPruner 的预热步数等参数必须按该尺度解释。
- 不增加 Hyperband 等其他策略、多算法注册体系或自动选择剪枝策略；特殊需求交给自定义调参代码。
- 被剪枝 trial 记录为 pruned，不当作失败或重试。入口以 `search.pruning.strategy != "none"` 检查方法的实际剪枝能力；默认循环按完整 epoch（从 1 开始）报告，自定义 ragged 示例也明确使用 epoch 尺度。

### 7.3 异常、重试与并发边界

搜索、持久化和剪枝复用 Optuna 原生能力；可容忍异常通过 Python 异常类型的 `catch` 接入，不建设异常表达式或文本匹配系统。宽泛库异常如需容忍，应由研究代码识别后转换为专用异常。

已复核保留现有边界：catch 配置拒绝非 Exception 类，因此不接受 BaseException、KeyboardInterrupt、SystemExit；宽泛 Exception/RuntimeError 与平台错误不作为容忍项。Optuna 优先处理 TrialPruned 并标记 PRUNED，不因 catch 变为失败；不为这两类误报新增防御代码。

显式重试失败 trial 使用 `study.enqueue_trial(failed_trial.params)` 等原生入队能力：保留原 trial，新 trial 记录来源；只有已记录的参数能够固定，不自建重试系统。并行搜索时，队列中的重试 trial 可能被另一进程消费，不保证由发起重试的进程执行。该行为不等于 checkpoint 恢复，也不改变可容忍异常的默认处理。

继续 study、失败 trial 重试和实验组继续的行为分别以 PRD 第 5.5–5.6 节为准。当前实现使用 study 目录内的 Optuna SQLite RDBStorage；独立终端可显式继续同一 study，各自指定设备与追加预算，元数据修改持短锁。不采用线程并行，以免训练共享进程随机状态。此实现面向可靠本地文件系统的小规模并行，不承诺共享网络盘 SQLite 锁语义，不建设模板 GPU 调度系统或集群任务平台。

硬杀进程可能使 Optuna 留下 RUNNING trial。当前不自动判断其失效、恢复或重试；用户确认进程已停止后，可通过 Optuna 原生 API 显式标记失败，再按既有流程重试。这是运行限制，不代表模板提供故障自动恢复保证。

### 7.4 采样器与预算

仅支持 TPE（默认）和 Grid，直接使用 Optuna 原生采样器，不建注册框架。两者 seed 均复用显式填写的 config.seed；trial 训练不按 trial 编号更换 seed。不持久化采样器内部随机状态，也不保证跨进程续跑或并行的轨迹完全一致。

TPE 仅开放以下五项，未填写项通过当前 Optuna 构造签名补全，不固定模板默认值，显式填写优先；配置使用 `search.sampler.strategy = "tpe" / "grid"` 和 `search.sampler.params`；TPE 参数表允许省略或部分填写，Grid 不接受该参数表：

| 参数 | 默认生效值 | 约束/说明 |
|---|---|---|
| n_startup_trials | 10 | 不随本次预算缩放，继续搜索利用已有 trial |
| n_ei_candidates | 24 | 原生候选数量 |
| multivariate | None（自动） | 不强制转换为 true；由当前 Optuna 按研究类型选择 |
| group | false | 与显式 multivariate=false 冲突时报错；自动模式交由 Optuna |
| constant_liar | true | 使用原生行为，尚标 RUNNING 的残留 trial 也会影响采样 |

上述数值仅说明 Optuna 5.0.0，不是模板固定默认。补全的非 None 值进入生效配置；原生 None 使用省略参数表达（TOML 不支持 null），不冻结库的自动行为。seed 仍使用实验 seed。旧配置中的明确值不自动改写，复现应保留依赖锁文件。

Grid 复用 search.space 的 categorical/choices，所有搜索参数及有限候选须预先列明；首次使用显示组合总数。允许对已选参数作确定性派生；请求未列出的动态搜索参数时报错，研究者应主动选择 TPE，不自动切换或离散化。CLI 与 Python 都要求显式给出本次追加 trial 预算，网格耗尽则提前结束，不为凑预算继续。

### 8.2 统计实现约定

#### 适用范围与现有计算

- 输入为两个方法多次运行的逐次指标，不是两个均值。两侧分别来自同一方法/训练设置，seed 唯一且完全对应，记录集合不重叠；沿用数据集与评估协议检查，至少需要两对结果。
- 模板按 seed 对齐，但相同 seed 不自动证明配对合理。研究者负责合理配对、各对的适当独立性及统计假设；少量 seed 的检验能力有限，不能保证满足所有论文评审要求。
- 配对 t 检验关注差值均值，尤其小样本时需考虑差值分布的正态假设；Wilcoxon 符号秩检验也有适用假设（通常要求差值分布对称），不是 t 检验不显著时自动替换的补救选项。
- 两侧描述性标准差使用样本标准差 `ddof=1`；平均差值固定为 left − right，单位与原指标一致，不自动推断提升方向。
- CLI 与 Python 均要求明确选择 ttest 或 wilcoxon，不设默认检验。
- 检验均为双侧。t 检验使用 SciPy `ttest_rel`；Wilcoxon 使用 `zero_method="wilcox"`、`alternative="two-sided"`、`method="auto"`。这些是本模板采用的计算约定，并非唯一正确方法。
- 研究者应事先确定检验与显著性阈值，不根据哪个结果显著来挑选。模板不自动进行正态性检测、选择检验、判定方法优越或输出 `significant` 布尔结论。
- 不增加独立样本、逐样本预测、多方法批量检验或多重比较校正；实际设计超出适用范围时，应使用相应研究分析，而非强套当前接口。

#### 已实现的检验输出

保留现有 `paired()` 和 CLI 命令，在同一次结果中返回：

| 字段 | 含义 |
|---|---|
| `pairs` | 有效配对数量 |
| `left.mean` / `left.std` | 左侧均值与样本标准差 |
| `right.mean` / `right.std` | 右侧均值与样本标准差 |
| `mean_difference` | left − right 的平均差值 |
| `test` | 用户选择的检验名称 |
| `alternative` | `two-sided` |
| `p_value` | p 值；检验未计算时为 null |
| `status` | `ok` 或 `not_computed` |
| `reason` | 未计算时的明确原因 |

复用已读入的逐次指标及 NumPy/SciPy，不建立新结果管理系统。

输入错误（数据集/协议不兼容、配对缺失或重复、非有限指标等）仍明确报错。对输入可比较但检验退化的情形，如配对 t 检验的差值无方差、当前 Wilcoxon 约定下的全零差值，保留描述性结果，返回 `p_value=null`、`status="not_computed"` 和原因。不得编造 p 值、自动更换检验，或把任意异常都吞成“未计算”。这是模板选择的报告方式，不将所有退化情况表述为普遍统计定律；其他未约定异常保留原生错误。

`paired()` 及原 CLI 命令已输出上述字段（`left` / `right` 为包含 `mean/std` 的字典，`reason` 仅在未计算时出现）。无方差判断使用差值是否全部相等，避免常量浮点数组的标准差舍入误差。没有异常兜底或自动换检验；原测试已补充正常描述性结果、两类退化结果、CLI JSON 输出和输入错误检查。

## 9. 验证与后续落实

验证聚焦模板关键校验、覆盖与写入互斥、默认流程、恢复有效记录以及公共能力，不认证研究方法，不扩大为理论故障矩阵。

采用 Ruff 格式化/lint、精简 pytest 与轻量示例，不设全量静态类型检查门禁或覆盖率目标。执行顺序、验收命令、GitHub Actions 双系统 CPU 验证、本地 GPU 验证及外部平台实测边界统一见 [单阶段实施计划](ImplementationPlan.md#4-验证与验收)。

实现采用 filelock、Optuna SQLite、SciPy，以及默认线性分类和变长字典自定义回归两个轻量示例。实际验证与未完成项见实施计划。若需要改变上述职责或行为，重新确认，不以实现便利扩大范围。
